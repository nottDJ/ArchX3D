## 1. Principles

**Semantic names, not literal ones.** A component says `bg-surface`, never
`bg-zinc-900`. The literal is an implementation detail of the theme; the
semantic name is the contract. This is what made a two-theme product possible
from a one-theme codebase in a single pass.

**Every value has a reason.** Not "8px looks right" but "8px, because the
control inside it is 6px and nested radii must step down". A scale whose values
cannot be defended gets extended arbitrarily the first time someone needs
something in between.

**Fewer steps than you think you need.** Four text colours, three elevations,
six radii, five durations. Every additional step is a decision a future
contributor has to make correctly, and the marginal one is almost never worth
the ambiguity it introduces.

**Light and dark are counterparts, not variants.** Both themes assign meaning
to the same ramp positions, so a component written once is legible in both with
no conditional anywhere.

## 2. Token architecture

Three layers. Components only ever touch the third.

```
┌─ 1. PRIMITIVE RAMPS ────────────────────────────────────────────────┐
│  --neutral-1 … --neutral-12    --accent-1 … --accent-12             │
│  --success-{3,6,9,11}  --warning-{…}  --danger-{…}                  │
│  Raw OKLCH. Redefined per theme. Never referenced by a component.   │
└─────────────────────────────────────────────────────────────────────┘
                                  ↓
┌─ 2. SEMANTIC ALIASES ───────────────────────────────────────────────┐
│  --surface  --surface-hover  --text-primary  --border  --accent-solid│
│  Names a *role*. Identical in both themes; only the ramp changes.   │
└─────────────────────────────────────────────────────────────────────┘
                                  ↓
┌─ 3. TAILWIND UTILITIES ─────────────────────────────────────────────┐
│  bg-surface  text-primary  border-line  bg-accent-solid             │
│  What components write. Generated by @theme inline.                 │
└─────────────────────────────────────────────────────────────────────┘
```

**Why the middle layer exists.** Without it, changing "secondary text" from
step 11 to step 10 means editing every component. With it, it is one line, and
the change is reviewable as a *design decision* rather than a diff of 200
files.

## 3. Colour ramps

### The 12 steps

Radix's convention, because the steps carry meaning rather than just
brightness:

| Step | Role |
| --- | --- |
| 1 | App canvas |
| 2 | Subtle surface |
| 3 | Component background |
| 4 | Component hover |
| 5 | Component active |
| 6 | Subtle border |
| 7 | Border |
| 8 | Strong border, focus ring |
| 9 | Solid fill |
| 10 | Solid fill hover |
| 11 | Low-contrast text |
| 12 | High-contrast text |

This is what makes the themes honest counterparts: `--neutral-11` is
"secondary text" in light *and* dark, so `text-secondary` needs no conditional.

### Why OKLCH

Three concrete reasons, not fashion:

1. **Perceptually uniform lightness.** Step 9 has the same visual weight across
   every hue, so the semantic colours cannot end up with one shouting louder
   than the others. In HSL, `hsl(220 90% 50%)` and `hsl(60 90% 50%)` differ by
   roughly 40% in perceived lightness — which is why yellow warnings always
   look wrong beside blue accents in HSL-based systems.
2. **Interpolation stays in gamut.** Mixing two OKLCH colours does not drift
   through grey the way HSL does.
3. **Wide gamut for free.** On a P3 display the accent renders more saturated
   without a second definition.

### Neutral

Very slightly cool — hue 250, chroma 0.004–0.014. A pure grey reads as cheap on
a large surface; a trace of blue reads as considered. The chroma is deliberately
below 0.015 so it never reads as *blue*, only as *not flat*.

| Step | Dark | Light |
| --- | --- | --- |
| 1 | `oklch(0.155 0.006 250)` | `oklch(0.994 0.001 250)` |
| 2 | `oklch(0.185 0.007 250)` | `oklch(0.980 0.002 250)` |
| 3 | `oklch(0.222 0.008 250)` | `oklch(0.960 0.003 250)` |
| 4 | `oklch(0.252 0.009 250)` | `oklch(0.943 0.004 250)` |
| 5 | `oklch(0.284 0.010 250)` | `oklch(0.925 0.005 250)` |
| 6 | `oklch(0.324 0.011 250)` | `oklch(0.900 0.006 250)` |
| 7 | `oklch(0.378 0.012 250)` | `oklch(0.866 0.008 250)` |
| 8 | `oklch(0.458 0.014 250)` | `oklch(0.790 0.011 250)` |
| 9 | `oklch(0.552 0.014 250)` | `oklch(0.558 0.014 250)` |
| 10 | `oklch(0.612 0.013 250)` | `oklch(0.508 0.014 250)` |
| 11 | `oklch(0.742 0.010 250)` | `oklch(0.452 0.013 250)` |
| 12 | `oklch(0.962 0.004 250)` | `oklch(0.218 0.010 250)` |

Note that step 9 is nearly identical in both themes: a mid-grey solid reads the
same either way, which is why it works for a disabled fill in both.

### Accent

Hue 252 — a calm architectural blue. **Deliberately not the saturated violet
that marks a product as an AI demo**, and not a cyan, which reads as
consumer-tech. Chroma peaks at 0.155 (dark) / 0.185 (light): high enough to be
unmistakably the accent, low enough not to vibrate against the neutral.

Light mode uses higher chroma because a saturated colour on white needs more
of it to carry the same weight it has on near-black.

### Semantic hues

| Intent | Hue | Chosen because |
| --- | --- | --- |
| success | 158 | Green, shifted toward teal so it is distinguishable from the accent for a deuteranope |
| warning | 78 | Amber, not yellow — yellow at AA contrast on light backgrounds is nearly brown |
| danger | 22 | Red-orange rather than pure red, which is harder to read at small sizes |

Only four steps each (3, 6, 9, 11): surface, border, solid, text. The full 12
would be unused weight.

## 4. Semantic colour

### Surfaces

| Token | Utility | Role |
| --- | --- | --- |
| `--surface-canvas` | `bg-canvas` | The page |
| `--surface-subtle` | `bg-subtle` | Sidebar, inset regions |
| `--surface` | `bg-surface` | Cards, panels |
| `--surface-hover` | `bg-surface-hover` | Hovered row or card |
| `--surface-active` | `bg-surface-active` | Pressed, or a track |
| `--surface-raised` | `bg-raised` | Dialogs, menus, popovers |
| `--surface-sunken` | `bg-sunken` | Inputs, wells, code |
| `--surface-overlay` | `bg-overlay` | Modal scrim |

### Text

Four levels. A fifth is always a mistake in disguise.

| Token | Utility | Use |
| --- | --- | --- |
| `--text-primary` | `text-primary` | Headings, values, the thing being read |
| `--text-secondary` | `text-secondary` | Body, labels |
| `--text-tertiary` | `text-tertiary` | Metadata, hints, captions |
| `--text-disabled` | `text-disabled` | Inert controls only |
| `--text-on-solid` | `text-on-solid` | On any solid fill |

### Borders

| Token | Utility | Use |
| --- | --- | --- |
| `--border-subtle` | `border-line-subtle` | Dividers, flat card edges |
| `--border` | `border-line` | Inputs, raised cards |
| `--border-strong` | `border-line-strong` | Hover, emphasis |

### Intent

Each intent has four tokens with identical structure, so they are
interchangeable in a component that takes a `tone`:

```
{intent}-surface    tinted background
{intent}-border     border on that background
{intent}-solid      filled button, dot, bar
{intent}-text       text on the tinted background
```

`accent`, `success`, `warning`, `danger`.

## 5. Theming

### Three choices

Light, dark, system — selected in the header, persisted to `localStorage`.
System follows the OS *live*, including when it switches at sunset.

### Applying a theme

`data-theme="light"` or `"dark"` on `<html>`, plus `color-scheme` so the
browser renders native scrollbars, form controls and the root background to
match. Omitting `color-scheme` gives a dark page light scrollbars, which reads
as a bug.

### No flash of wrong theme

`THEME_SCRIPT` in `lib/theme.ts` is inlined into `<head>` and runs **before
first paint**:

```js
var stored = localStorage.getItem('archx3d.theme');
var theme = stored === 'light' || stored === 'dark' ? stored
  : (matchMedia('(prefers-color-scheme: light)').matches ? 'light' : 'dark');
document.documentElement.setAttribute('data-theme', theme);
```

It must be inline. A deferred module executes *after* the paint it exists to
prevent, which is the white flash every themed app is known for.

### Dark mode is not inverted light mode

Two things change beyond the ramp:

**Shadows carry almost nothing.** There is no light source for a surface to
cast against. Elevation is carried by surface lightness plus a 1 px inset top
highlight (`--highlight`, applied by `.edge-highlight`). The shadow stays only
to anchor the element.

**Borders do more work.** `--shadow-strength` is 0.5 in dark and 0.06 in light,
because a shadow that reads correctly on white is invisible on near-black, and
one tuned for dark is a smear on white.

## 6. Typography

### Families

| Token | Family | Use |
| --- | --- | --- |
| `--font-sans` | Inter | Everything |
| `--font-mono` | JetBrains Mono | IDs, filenames, sizes, logs, coordinates |

Both via `next/font` with `display: swap`. Inter uses `adjustFontFallback` so
the metrics of the fallback match and the swap does not reflow. JetBrains loads
**only weights 400 and 500** — the full family is ~180 kB of faces nothing
renders.

### Scale

1.20 minor third, rounded to whole pixels, clamped at both ends.

| Token | px | Line | Use |
| --- | --- | --- | --- |
| `text-2xs` | 11 | 16 | Metadata, keyboard hints, table headers |
| `text-xs` | 12 | 18 | Labels, captions, secondary rows |
| `text-sm` | 13 | 20 | **Default UI size** |
| `text-base` | 14 | 24 | Body copy |
| `text-md` | 16 | 26 | Lead paragraphs |
| `text-lg` | 18 | 26 | Card titles |
| `text-xl` | 22 | 30 | Page titles |
| `text-2xl` | 28 | 36 | Section heroes |
| `text-3xl` | 36 | 42 | Landing headline |
| `text-4xl` | 48 | 52 | Landing hero, large screens |

**Clamped at 11 px** because below that hinting collapses and a "scale" becomes
whatever the renderer does. **Clamped at 48 px** because nothing in this
product needs a larger distinct step.

### Weights

400 regular, 500 medium, 600 semibold. **No bold (700).** At 13 px, 600 is
already emphatic and 700 muddies at small sizes.

### Global settings

```css
body { font-variant-numeric: tabular-nums; }   /* figures never jitter */
h1,h2,h3,h4 {
  font-variant-numeric: normal;                /* a title is prose */
  letter-spacing: -0.014em;                    /* tightens at display sizes */
  text-wrap: balance;                          /* no orphaned words */
}
p { text-wrap: pretty; }
```

## 7. Spacing

4 px base. The permitted values, and what each is for:

| Value | px | Use |
| --- | --- | --- |
| `0.5` | 2 | Hairline offsets only |
| `1` | 4 | Icon to label |
| `1.5` | 6 | Button internal gap |
| `2` | 8 | Related items in a row |
| `3` | 12 | Items within a group |
| `4` | 16 | **Card padding, list rows — the default** |
| `5` | 20 | Dialog padding |
| `6` | 24 | Between sections |
| `8` | 32 | Between major regions |
| `10` | 40 | Page vertical rhythm |
| `12` | 48 | Page top margin |
| `16`, `20` | 64, 80 | Landing sections only |

A value not on this list means the layout is wrong, not the scale.

## 8. Radius

**Nested radii are concentric.** A control inside a card inside a panel steps
*down*, or the nesting reads flat — this is the commonest reason an interface
looks slightly wrong without anyone being able to name it.

| Token | px | Use |
| --- | --- | --- |
| `rounded-xs` | 4 | Badges, tags, `kbd` |
| `rounded-sm` | 6 | Small controls, menu items |
| `rounded-md` | 8 | **Buttons, inputs** |
| `rounded-lg` | 12 | Cards, menus, popovers |
| `rounded-xl` | 16 | Dialogs, panels |
| `rounded-2xl` | 20 | Hero surfaces |
| `rounded-full` | — | Dots, pills, avatars |

The rule of thumb: inner radius ≈ outer radius − padding.

## 9. Elevation

Five shadow tokens, three card elevations. Each tied to a **job**, not a depth
in pixels.

| Elevation | Shadow | Job |
| --- | --- | --- |
| `flat` | none + border | Content grouped on the canvas |
| `raised` | `shadow-sm` + border + highlight | A discrete object you can act on |
| `floating` | `shadow-lg` + border + highlight | Temporarily above the page |

`shadow-md` and `shadow-xl` exist for hover on a card and for dialogs
respectively; they are not separate *elevations*.

Shadows are two-layer — a tight contact shadow plus a wide diffuse one —
because a single blur reads as a sticker. Both scale with
`--shadow-strength`, which is theme-dependent.

**Picking a shadow because it looks nicer is how a system ends up with five
depths and no meaning.** If a card must look more important than its
neighbour, that is a hierarchy problem.

## 10. Motion

| Token | ms | Use |
| --- | --- | --- |
| `--duration-instant` | 80 | Hover, focus |
| `--duration-fast` | 120 | Press, toggle, tooltip |
| `--duration-normal` | 180 | Panel, menu, fade |
| `--duration-slow` | 260 | Page transition, toast |
| `--duration-deliberate` | 400 | Camera flight — literal travel |

| Easing | Curve | Use |
| --- | --- | --- |
| `--ease-standard` | `cubic-bezier(0.2, 0, 0, 1)` | Almost everything — decelerates into place |
| `--ease-emphasised` | `cubic-bezier(0.34, 1.4, 0.64, 1)` | Slight overshoot, for things that should feel physical |
| `--ease-exit` | `cubic-bezier(0.4, 0, 1, 1)` | Leaving — accelerate away |

**Why so short.** 120 ms reads as instant-but-not-jarring. Anything over 300 ms
in a productivity tool reads as *latency*, and a user who repeats an action
fifty times a day comes to resent it.

### Named animations

`animate-fade-in`, `animate-rise-in`, `animate-scale-in`,
`animate-slide-right`, `animate-slide-left`, `animate-spin-slow`,
`animate-pulse-soft`, `animate-shake`, plus `.skeleton` and `.stagger`.

### Reduced motion

`prefers-reduced-motion: reduce` collapses animation and transition durations
to 0.01 ms and replaces the skeleton shimmer with a flat fill. Opacity
transitions survive — a state change with no feedback at all is worse than a
subtle one — and nothing that conveys information depends on movement.

## 11. Layout

| Token | Value | Use |
| --- | --- | --- |
| `--spacing-sidebar` | 15 rem | Navigation width |
| `--spacing-topbar` | 3.25 rem | Header height, all surfaces |
| `--container-prose` | 44 rem | Prose — max ~75 characters |
| `--container-content` | 68 rem | Forms, wizard, landing |

Breakpoints are Tailwind's defaults; only `sm` (640), `lg` (1024) and
occasionally `xl` (1280) are used. More breakpoints means the layout is
fighting itself.

## 12. Layers

Explicit, because a `z-index` arms race is a guaranteed outcome otherwise.

| z | Layer |
| --- | --- |
| 0 | Content |
| 10 | Sticky within content |
| 20 | Viewer floating chrome |
| 30 | App header, side panels |
| 40 | Mobile nav scrim |
| 50 | Sidebar drawer, dialogs, menus, tooltips |
| 60 | Command palette, toasts |
| 70 | Skip link |

The skip link is highest deliberately: it must be reachable even when a modal
is open.

## 13. Using tokens

### In a component

```tsx
// ✓
<div className="rounded-lg border border-line bg-surface p-4">
  <h3 className="text-sm font-semibold text-primary">Title</h3>
  <p className="mt-1 text-xs text-tertiary">Supporting copy</p>
</div>

// ✗ — literals, arbitrary spacing, arbitrary size
<div className="rounded-[10px] border border-zinc-800 bg-zinc-900 p-[15px]">
  <h3 className="text-[13px] font-semibold text-white">Title</h3>
</div>
```

### In raw CSS

```css
.thing {
  background: var(--surface);
  color: var(--text-primary);
  border-radius: var(--radius-lg);
  transition: background-color var(--duration-fast) var(--ease-standard);
}
```

### The `className` rule

**A component owns its appearance; the caller owns its position.** Pass layout
utilities — `w-full`, `mt-4`, `col-span-2`. Do not pass colours or typography:
if a component needs to look different, that is a variant, and a variant is
reviewable in a way an ad-hoc override is not.

`cn()` uses `tailwind-merge` with the custom scale names registered, so a
legitimate override resolves predictably rather than depending on the order
Tailwind happened to emit the two classes.

## 14. Extending the system

### Adding a token

1. Can an existing one do the job? Usually yes.
2. Add the primitive to **both** themes.
3. Add the semantic alias.
4. Expose it in `@theme inline`.
5. If it is a colour, register it in `cn.ts`'s class groups — otherwise
   `tailwind-merge` will treat it as conflicting with a size utility and
   silently drop one.
6. Document it here.
7. Check contrast in both themes.

### Adding a colour

Requires an ADR-style justification: which existing intent it is not, what it
means, and its contrast at steps 9 and 11 in both themes. Four intents plus
neutral covers everything this product currently expresses.

### Never

- A literal colour in a component
- An arbitrary value where a scale step exists
- A theme-conditional in a component (`dark:` should not be needed — tokens
  already resolve)
- A new shadow without a new *job* for it
